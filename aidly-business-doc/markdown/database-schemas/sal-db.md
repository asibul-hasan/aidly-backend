# SAL DB Script

<!-- Consolidated from the previous aidly-business-doc/backend, frontend, memory, and planning files. -->

PUR and SAL share the current migration script because they are commercially coupled through AR/AP and inventory/finance postings. SAL-owned sections define customers, sales invoice/POS, receipts, returns, and AR ledger support.

### 2026-08-14 — contract & posting audit (no schema change)

An audit comparing each form's frontend field vocabulary against its backend DTOs,
and every emitted GL event against `fin_gl_map`, found these **in the code, not the
schema** — the database was right throughout and needed no migration:

| Form | Defect | Effect |
|---|---|---|
| SAL_1001 | DTO exposed `discount_percent` / `tax_percent`; the form sends `line_discount_pct` / `tax_rate_pct` (the real column names) | **every line discount and tax rate saved as zero** |
| SAL_1001 | Line money was taken from the client | discount/tax amounts now derived server-side from the rates |
| SAL_1001 | Cancel reversed stock and AR but emitted no GL event | GL kept the revenue, VAT and COGS of a cancelled sale **permanently** |
| SAL_1001 / SAL_1103 | Read paths never populated product or UOM names | blank product and unit columns on every saved document |
| SAL_1103 | `net_unit_price`, `tax_rate_pct`, `restock_flag`, `batch_code`, `return_reason`, `refund_method` were all sent by the form and dropped | returns credited at the wrong price with the wrong GL leg |
| SAL_1103 | Post restocked **every** line regardless of `restock_flag` | damaged and expired returns went back on the shelf as sellable |
| SAL_1103 | `RefundAgainstDue = 2`, but 2 is Card and 6 is AgainstDue | card refunds credited the customer's receivable; real against-due refunds never touched it |

`sal_invoice_dtl.line_discount_pct` / `tax_rate_pct` and `sal_return_dtl.net_unit_price` /
`restock_flag` existed all along — only the DTO layer disagreed with them.
